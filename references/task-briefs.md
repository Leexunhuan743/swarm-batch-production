# 子代理任务书骨架

任务书应短而完整，不依赖“代理自然知道上下文”之类隐式前提。

所有任务书至少写清：**角色、目标、必读输入、唯一输出路径、允许写的范围、禁止修改项、验收方式、上报条件、回复格式**。

要求读取文件时，让代理读取内容本体；目录列表、文件名、摘要、截断日志都不能冒充“已读”。

## A. 示范对抗审查

```text
角色：独立只读审查者
目标：审查 <exemplar paths>，寻找一旦复制到整批会被放大的问题。

必须读取：
- <权威输入/需求>
- <base exemplar 1>
- <base exemplar 2>
- <relevant type exemplar, if any>

只允许写：
- work/review-staging/<review_task_id>/report.md

禁止：
- 修改示范、spec、权威输入或任何其他文件
- 查看或询问其他同岗审查者的报告
- 用“个人风格偏好”冒充正确性问题

至少检查：
- 正确性 / 完整性
- 可复制性
- 第一单元特殊规则是否被误当通用规则
- 结构、术语、接口、边界条件
- 失败处理与环境依赖（适用时）

每条问题写：位置 + 发现 + 依据/验证理由 + 优先级 + 建议。
另列：已检查且确认正常的关键项；不确定项单独列出。

回复：只报 report 路径、问题数、阻塞项；不要把全文复制回聊天。
```

## B. 批量生产

```text
角色：生产作者
负责：<unit_id(s)>
输出：<exact output path(s)>

必须读取：
- spec/spec.md
- <base exemplar 1>
- <base exemplar 2>
- <relevant type exemplar, if any>
- <unit-specific inputs>

公共形态已经定型：
- 不重新设计公共结构
- 只在 spec 标注的可变区域内发挥

只允许写：
- <自己的输出路径>
- 必要临时文件只能进 <work path>

禁止修改：
- spec/
- 权威输入
- 他人产物
- reviews/
- 用户未授权路径

自检：
- 只跑和自己单元直接相关的局部检查
- 不重复跑全批/全库检查，除非任务书明确要求

遇到以下情况立即上报主代理，不自行发明规则：
- spec 与输入冲突
- 依赖缺失
- 存在两种会影响公共约定的解释
- 需要写出授权范围

回复：输出路径 + 局部自检结果/数字 + 阻塞项。
```

## C. Peer review（复用生产代理）

```text
角色：独立 peer reviewer
目标：审查 <target_unit_id> 的当前产物。

必须读取：
- <target output>
- spec/spec.md
- 两个基础示范 + 与目标相关的类型示范（若有）
- 与目标直接相关的依赖（需要时）

只允许写：
- work/review-staging/<review_task_id>/report.md

禁止：
- 修改被审产物
- 修改任何其他文件
- 查看另一位 reviewer 的报告、staging 路径或结论
- 因为知道自己原来的写法而强迫目标照抄自己的局部风格

重点：
- spec 遵守情况
- 是否真正遵循示范的共性，而不是只仿表面
- 局部正确性
- 与相邻/依赖单元的衔接
- 重复、遗漏、引用/接口错位

每条反馈写：具体位置 + 发现 + 证据/依据 + 优先级 + 建议。
不确定项单列，交主代理裁决。
```

主代理派工时不告诉 reviewer 另一位是谁，也不把另一份报告路径放进上下文。能并发派发就并发派发。目标单元第一版和两位 reviewer 的生产任务都就绪后即可派发该目标的 peer review，不必等待无关单元全部完成；存在真实全局依赖时再显式等待。

## D. 原作者修订（必须优先复用原作者）

```text
角色：<unit_id> 的原作者
输入：
- 自己的当前产物
- spec/spec.md
- 两个基础示范 + 与目标相关的类型示范（若有）
- review A
- review B
- 相关 DECISIONS 条目（若有）

逐条把意见分为：
1. 接受：说明怎么改，并实际修改
2. 拒绝：说明为什么不适用
3. 上报：两份意见冲突、事实不确定、会改变公共规则、影响他人单元

只允许修改自己的产物和明确授权的临时文件。
不得为“通过检查”去改 spec、权威输入、review 或他人产物。

修改后重跑本单元局部自检并报结果。
```

如果宿主无法恢复原作者上下文，替代代理必须读取原产物、两份反馈、spec、示范和相关裁决；manifest 标记 `author_replaced`，不要假装是原会话续写。

## E. 纵向一致性审查（必须用新代理）

```text
角色：新的纵向审查者
维度：<dimension_id，例如“所有第一节/所有错误处理/所有字段 X”>

必须读取：
- 当前全部相关交付产物
- spec/spec.md
- 两个基础示范 + 与目标相关的类型示范（若有）

通常不要读取：
- peer review 报告
- 同期其他纵向 reviewer 的报告

只允许写：
- reviews/vertical/<dimension_id>__vertical-review__<reviewer_id>.md
  （或先写独立 staging，再由主代理提升）

只审这个纵向维度，重点找跨单元漂移：
- 术语
- 格式
- 结构
- 接口/签名
- 默认值
- 命名
- 引用/链接
- 其他 spec 要求的一致性

每条问题写：涉及单元 + 差异 + spec/示范依据 + 建议统一方式。
可以指出“当前最清晰的候选示例”，但它不是自动标准。
不修改任何产物。
```

## F. 主代理派工前核对

每批任务发送前机械检查：

- 每个输出路径唯一；
- reviewer 不会自审；
- 同一目标的两位 reviewer 是不同 `agent_id`；
- 任务书只授权必要写入；
- 必读路径真实存在；
- 共享规则来自同一份 spec，不复制出多份轻微不同的契约；
- 没有把某次宿主的固定并发上限写成通用事实。

## G. Review 报告最小格式

```md
# Review: <target> by <reviewer>

Spec: <revision>
Task: <review_task_id>

## 必须修
- [位置] 发现：...
  依据：...
  建议：...

## 建议修
...

## 不确定 / 交主代理
...

## 已验证正常
- ...

## 验证记录
- 读取/检查了什么：...
- 可复跑的命令或方法：...
```

不要要求所有项目都使用统一严重度术语；能稳定区分“必须修 / 建议 / 不确定”通常就够。
