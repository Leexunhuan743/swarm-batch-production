# Swarm Batch Production

一个通用的 **多代理批量生产 Skill**，适用于支持 Skill / 子代理工作流的 Agent。

适用于“同一份规范要重复落到几十份产物”的任务——文档、Markdown/HTML 页面、代码模块、配置、测试、SQL、数据片段等。它要解决的核心矛盾是：批量产出容易快，但容易彼此漂移；逐件精修质量高，但无法并行。

## 核心思路

**先做对，再做多。**

不要在开始时就凭空写一份 spec，然后祈祷所有单元都符合它。而是：

1. 主代理亲手做 2 个示范单元，做到可当模板的质量；
2. 多个子代理**独立、对抗地**审查示范，专找“复制几十次后会被放大”的问题；
3. 主代理裁决并修订示范；
4. **从已经稳定的示范反推 spec**——规范来源于经过审查的真实实现，而不是反过来。

之后才是并行批量生成、双人独立互审、原作者复修、纵向一致性审查。

## 三条主线

| 阶段 | 做什么 |
|---|---|
| **0–4 定型** | 拆分单元 → 主代理做示范 → 独立对抗审查 → 裁决修订 → 反推 spec |
| **5–7 批量** | 并行生成 → 复用生产代理做双人独立互审 → 复用原作者读完两份反馈后修订 |
| **8–11 收口** | 一批**新**代理做纵向一致性审查 → 主代理统一裁决 → 完成检查 |

横向与纵向审查故意用不同观察条件：横向 reviewer 复用生产作者，带着生成上下文，擅长发现局部正确性、相邻衔接、接口错位；纵向 reviewer 换新代理，把多个单元沿同一维度并排比较，擅长发现术语、格式、命名的漂移。两者不能互相替代。

## 五个不可省的保证

无论批次多小，这几条都不该被简化掉：

- 示范由主代理亲手做，并经过独立对抗审查后才抽象出 spec；
- 每个生产单元恰好收到**两份不同 reviewer 的独立**反馈；
- 每个单元由**原作者**读完两份反馈后修订（保留作者上下文）；
- 纵向一致性审查由**全新代理**完成；
- 冲突与不确定项由**主代理**裁决，不靠多数票。

## 目录结构

```text
<project-root>/
  deliverables/        # 最终交付产物；只放当前有效版本
  spec/
    spec.md            # 当前正式规范
    manifest.json      # 单元、角色、状态、映射的唯一台账
  reviews/
    exemplar/          # 示范的对抗审查
    peer/              # 每个单元的两份独立互审
    vertical/          # 纵向一致性审查
    DECISIONS.md       # 全局裁决，稳定编号
  work/
    drafts/            # 可丢弃草稿
    review-staging/    # 每个独立审查任务自己的隔离落点
```

职责分离是硬要求：`deliverables/` 不放草稿，`reviews/` 不与 `work/` 混用。已有项目结构可以映射，但主代理必须先声明映射关系。

**审查隔离**分三层：文件隔离（各自独立 staging）、信息隔离（不把另一份报告的路径或结论放进 reviewer 上下文）、次序隔离（同岗 reviewer 并发派发，不等一份落盘才启动另一份）。两份都完成后，才由主代理以唯一文件名提升到 `reviews/peer/`——文件名撞车属于静默数据丢失，不是命名风格问题。

## 安装

将仓库克隆到你的 Agent / 工具所使用的 Skills 目录：

```bash
git clone https://github.com/Leexunhuan743/swarm-batch-production.git \
  <skills-dir>/swarm-batch-production
```

具体 Skills 目录、发现机制和自动加载方式以所使用的宿主工具为准。

## 机械核对

`references/check-manifest.py` 只检查**确定性不变量**，不替代判断：

```bash
python references/check-manifest.py --root .                  # 阶段 0 结构检查
python references/check-manifest.py --root . --require-final  # 阶段 11 收口
```

覆盖：`unit_id` 与输出路径唯一；必要字段存在；reviewer 不自审、两位 reviewer 身份不同；review 分配与完成数量符合当前状态；review 路径不被重复引用、声明文件真实存在；`--require-final` 时全部达到最终状态。精确状态语义见 `references/spec-and-layout.md`。

它**不**检查审查关系是否 A↔B、不猜文件名是否违规、不验证内容质量、不根据多数票改 spec。

manifest 默认用 `spec/manifest.json`，仅需 Python 标准库；项目已有 YAML 约定时也可用 `manifest.yaml`，但运行检查器需要 PyYAML。

示范单元以 `role: exemplar` 标识，完成后使用 `status: exemplar-final`；它们豁免阶段 6 的两份标准 peer review，因为已经经过示范审查。

## 文件

| 文件 | 内容 |
|---|---|
| `SKILL.md` | 完整工作流：角色、阶段 0–11、失败与异常处理、使用原则 |
| `references/spec-and-layout.md` | 目录、ID、命名、manifest 字段、状态机、spec 最小内容 |
| `references/task-briefs.md` | 各类子代理任务书骨架，可直接套用 |
| `references/check-manifest.py` | manifest 不变量检查器 |

## 什么时候不要用

当批次很小、单元无法并行、或每个单元本来就需要独立设计时，**不要为了套流程而强行使用多代理**——直接生成，或“生成 + 抽检”即可。

流程本身是有成本的：每个生产代理动笔前都要读 spec 与示范，每个单元要额外经历两轮审查。只有“漂移是真实失效模式、且单元本身足够贵”时，这套机制才划算。数量只是信号，不设僵硬阈值。

## 使用原则

- **先做对，再做多。** 示范没稳定前，不开始大规模复制。
- **先有真实示范，再抽象 spec。** 规范来源于经过审查的实现。
- **作者上下文要复用，审查判断要隔离。** 这是全流程最重要的两个相反要求。
- **自述不是证据。** 子代理报出的“通过”只是线索；关键门禁由主代理或独立步骤复跑。
- **一致不等于正确。** 复制到全批的错误对所有一致性检查都是隐形的，只能靠独立于示范的依据（真实 schema、编译器、测试、上游接口）拦住。
- **范围控制比聪明更重要。** 批量代理只在授权路径内工作，不靠改 spec 或改权威输入让自己“看起来通过”。
- **不要为了流程而增加流程。**
